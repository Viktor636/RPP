# Лабораторная работа № 4 — асинхронная модель исполнения

Начальная реализация раздела III (задачи 3.1–3.6): PostgreSQL, генератор расписания, три заглушки авиапоставщиков, синхронный FastAPI-сервис, нагрузочный скрипт и профилирование через `py-spy`.

## 1. Что входит в проект

- `db/init.sql` — таблица `flights` и индексы по времени вылета и аэропорту.
- `backend/app/flight_generator.py` — воспроизводимая генерация рейсов.
- `backend/app/seed.py` — загрузка 1500 рейсов в сутки на 120 дней (всего 180 000).
- `providers/provider_app.py` — заглушка с задержкой, вероятностью HTTP 500 и вероятностью задержки 3 секунды.
- `backend/app/main.py` — синхронный поиск через `requests`, синхронный SQLAlchemy Core/psycopg и последовательный опрос поставщиков.
- `backend/app/route_builder.py` — построение прямых маршрутов и маршрутов максимум с двумя пересадками. Модуль не обращается к сети или БД.
- `load_test.py` — закрытая и открытая модели нагрузки, статистика для `/search` и периодические запросы `/health`.
- `docker-compose.yml` — PostgreSQL, три поставщика, однократная загрузка данных и сервис поиска.

## 2. Запуск в WSL / VS Code

Откройте эту папку в WSL. В терминале из корня проекта выполните:

```bash
cp .env.example .env
docker compose up --build -d
```

Первый запуск может занять несколько минут: Docker скачает образы, а контейнер `seed` создаст 180 000 рейсов. Проверьте состояние контейнеров:

```bash
docker compose ps
docker compose logs seed
docker compose logs search
docker compose exec db psql -U app -d flights_db -c 'SELECT count(*) FROM flights;'
```

Запрос к PostgreSQL после успешной загрузки должен показать `180000`. У сервиса поиска должны быть статус `healthy`, у `seed` — `Exited (0)` после успешной загрузки. Проверка API:

```bash
curl http://localhost:8000/health
curl 'http://localhost:8000/search?origin=OVB&destination=SVO&date=2026-10-26'
```

Swagger UI: <http://localhost:8000/docs>

В текущем `.env.example` расписание начинается **26 октября 2026 года** и продолжается 120 дней. Для теста передавайте дату в этом диапазоне. Генератор воспроизводим: фиксированная стартовая дата и seed дают одинаковые рейсы при повторном заполнении.

## 3. Нагрузочные замеры задачи 3.6

Скрипт использует `asyncio` и `httpx.AsyncClient`. Прогрев по умолчанию 10 секунд; далее измерение 60 секунд; тайм-аут запросов — 30 секунд.

Замкнутый режим, по одному клиенту:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt
python load_test.py --mode closed --clients 1 --duration 60 --warmup 10 --timeout 30
```

Повторите для `--clients 10`, `40` и `80`.

Открытый режим с интенсивностью 5 запросов/с:

```bash
python load_test.py --mode open --rate 5 --duration 60 --warmup 10 --timeout 30
```

Скрипт выводит количество запросов, фактическое число запросов/с, p50, p95, p99, максимум, процент ошибок и такие же показатели для `/health`. Вносите именно фактические цифры в таблицу 3; они зависят от компьютера и Docker.

## 4. Профилирование py-spy для задачи 3.6

Пока идёт нагрузка (например, запустите нагрузочный скрипт в другом терминале при `--clients 10`), выполните:

```bash
docker compose exec search py-spy record --pid 1 --duration 60 --output /profiles/sync_without_idle.svg
docker compose exec search py-spy record --pid 1 --duration 60 --idle --output /profiles/sync_with_idle.svg
```

Файлы SVG появятся в папке `profiles/` на вашей машине. Если Docker запрещает присоединение профилировщика, проверьте наличие `SYS_PTRACE` и `seccomp:unconfined` у `search` в `docker-compose.yml`.

В режиме без `--idle` py-spy в основном показывает активность Python-кода и обычно недооценивает время, когда поток ожидает сеть/БД. В режиме с `--idle` учитывается также состояние ожидания, поэтому можно оценить долю времени в ожидании внешнего ответа.

## 5. Команды остановки и повторного заполнения

```bash
docker compose down
```

Остановка без удаления данных. Чтобы удалить данные PostgreSQL и создать их заново:

```bash
docker compose down -v
docker compose up --build -d
```

**Внимание:** `seed` очищает таблицу `flights` и заново загружает фиксированный набор данных. Не запускайте его вручную, если в таблице есть данные, которые нужно сохранить.

## 6. Что осталось сделать после базовой синхронной версии

1. Выполнить замеры `C=1, 10, 40, 80` и открытую нагрузку 5 запросов/с.
2. Записать результаты в таблицу 3 и сохранить обе SVG-диаграммы.
3. Для задачи 4.1 заменить `def` на `async def`, не убирая блокирующие вызовы, и повторить тесты.
4. Для задачи 4.2 перейти на `httpx.AsyncClient`, асинхронный SQLAlchemy с `asyncpg`, `asyncio.gather`, `asyncio.timeout` и `asyncio.sleep`; после этого провести те же замеры.

Не заполняйте таблицу 3 предполагаемыми числами: используйте реальные результаты измерения.

## 7. Автоматические тесты вспомогательной логики

Из корня проекта, после активации `.venv` и установки dev-зависимостей:

```bash
pip install -r backend/requirements-dev.txt
pytest -q
```

Тесты проверяют повторяемость генератора, длительность перелёта и базовые ограничения построения маршрутов.
